## Through the lens

### A root daemon that took orders from anyone

Attackers got into Check Point firewall gateways through the PHP2Shell flaws in their Mobile Access portal, then became root with a new zero-day, CVE-2026-123039. A daemon running as root listened on a world-writable socket in `/tmp` and never checked which process was talking to it, so the portal's service account could simply ask it to run commands. The attackers then planted web shells (scripts that accept commands over HTTP) and a backdoor, moved over SSH to VMware ESXi hosts, and at some Israeli organisations ran a wiper that destroys data. Check Point says a couple of dozen customers were hit and has shipped fixes; CISA added the bug to its exploited list on November 13. **Connects to:** [Unit 1: Your lab, and Linux through a security lens](../units/lab-and-linux.html). Tuesday's lesson named a world-writable script run by a root cron job as a classic mistake; this is the same mistake with a socket. The file permissions let every user through, and the daemon never asked "who is asking?" itself, so like a careless SUID program it lent root's authority to anyone who wrote to it. ([BleepingComputer](https://www.bleepingcomputer.com/news/security/check-point-patches-zero-day-that-lets-hackers-get-root-access/), [BleepingComputer](https://www.bleepingcomputer.com/news/security/check-point-gateways-hacked-via-php2shell-to-deploy-vmware-esxi-wiper/), [The Hacker News](https://thehackernews.com/2026/11/hackers-exploit-php2shell-flaws-in.html))

### An SSH login bypass hidden in a single `*`

On Linux systems built on the musl C library that run OpenSSH without PAM, Alpine above all, a password of 257 to 1,024 characters made musl's password-hashing function fail and return `*`. Accounts with password login switched off store exactly `*` in `/etc/shadow`, so the failed result matched the stored value and the attacker was let in, privileged accounts included. OpenSSH 10.6p2 fixes it; researchers saw attacks within days of disclosure, and CISA added it to its exploited list on November 9. **Connects to:** [Unit 1: Your lab, and Linux through a security lens](../units/lab-and-linux.html). You met `/etc/shadow` on Tuesday as the file that holds password hashes; this bug is an error value being compared as if it were a hash, so the check passed when it should have failed. Two habits from the unit apply: turn off SSH password logins wherever keys will do, and know where logins appear in your authentication log. ([Ars Technica](https://arstechnica.com/security/2026/11/vulnerability-that-lets-hackers-ssh-into-linux-devices-is-under-active-exploitation/), [SecurityWeek](https://www.securityweek.com/openssh-rushes-patches-for-sshole-authentication-bypass/))

### A certificate authority loses eight more CAs

eMudhra, an Indian certificate authority (a company whose signatures browsers accept as proof of a website's identity), had 8 intermediate CAs revoked in October after one line in an in-house key-ceremony script cut their private keys to a single byte, so anyone could work the keys out from the public certificates. Its full incident report, posted this week, explains why it has now revoked 8 more: their keys weren't weakened, but they passed through the same script's memory, and the company can't show they were handled by its own rules. Microsoft starts removing eMudhra's remaining root certificates from Windows on November 16. **Connects to:** [Unit 4: Trust on the internet: DNS and TLS](../units/dns-and-tls.html). You'll meet this in unit 4: with the October keys, anyone could have issued a trusted certificate for any website, and only browsers that require every certificate to appear in public Certificate Transparency logs were safe from such forgeries. ([The Hacker News](https://thehackernews.com/2026/11/emudhra-revokes-8-more-cas-it.html), [SecurityWeek](https://www.securityweek.com/browsers-block-emudhra-intermediate-cas-over-recoverable-private-keys/))
